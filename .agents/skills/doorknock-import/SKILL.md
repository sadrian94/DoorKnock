# Import HiringCafe Saved jobs into DoorKnock

Read the repository's `AGENTS.md` and the job intake section of `workflow.md`. An import request authorizes saving the selected jobs locally. For an end-to-end import, include Analyze and Company Recon within the authorization for the operation. For an import-only request, skip both and account for the default recon behavior described below. Treat a request to check access as read-only. Keep applications, outreach, and individual gatekeeper research outside this workflow.

## Collect the listings

1. Use the HiringCafe plugin's saved-jobs tool when it returns the connected account's Saved stage. If it cannot retrieve the list, use the signed-in Chrome session and open HiringCafe Tracker → **Saved**. A website login and plugin account authorization are separate. If the tool asks you to retry after authorization, retry once and use the tracker if it still returns no data. If the tracker also requires sign-in, ask the user to sign in or supply the selected listings. Reconcile the Saved count or the requested subset, including any pagination or connector truncation.
2. For each job, capture its public HiringCafe job link, title, company, location, workplace type, pay and pay interval if supported, and the job description. In the browser, the job details' **Share this role** control exposes the public listing URL. Use the full description when available. Label a summary as such and avoid copying account identifiers, tracker notes, or referral parameters into DoorKnock.
3. Check the employer or its ATS for the matching requisition when available. Preserve the HiringCafe URL as the source. Record an employer application URL separately only when it identifies the same opening. Keep an unverified, inaccessible, or closed posting clearly labeled in the local record or report, as appropriate. A Saved card establishes what the user saved and may survive an expired posting.

## Import and enrich

1. Inspect existing DoorKnock records across stages before writing. Compare canonical listing URLs or requisition IDs first, then use normalized company and title with location or requisition details to resolve differences in wording. Keep existing job IDs, application stages, and timelines. Report ambiguous matches instead of merging them. Resume work on the same job IDs after a partial failure.
2. Use DoorKnock's import UI or `POST /api/jobs/import` with `source: hiringcafe` and the captured metadata. The request schema and writes live in `backend/app/api/import_job.py`. The route creates a job and application in **Saved**, copies `job_url` into both URL fields, and queues Company Recon. Keep a verified employer link in the posting notes if you cannot set `application_url` separately through the available local workflow. If the server is unavailable, call the same import handler locally with `ImportConfirmedJobRequest` and FastAPI `BackgroundTasks`, using the checkout's Python environment and configured database. Follow the database state through verified job IDs. Never leave `company_recon_status` at `pending` if using the local handler without dispatching its background task. Use the queued recon handler to dispatch it for an authorized full import, or clear the undelivered `pending` status on the new records for an import-only request. For import-only, use the local handler without dispatching the task because the default HTTP route queues recon.
3. Read the configured provider before sending anything. Analyze sends context from `workspace/master_resume/master_evidence.yaml` and the job description to that provider. Where external transmission needs separate approval, name the provider and payload and obtain authorization before running it. Company Recon sends the employer, role, public URL, and the posting description. Use public posting content only for that operation. Keep other authorized work moving if one operation is blocked, and do not work around an approval rejection.
4. For fit analysis on a saved job, call `POST /api/jobs/{job_id}/rematch`. For Company Recon on a saved job, first check whether recon completed or is already queued or running. Use `POST /api/jobs/{job_id}/recon` when a run is needed and no live task owns it. These handlers are in `backend/app/api/jobs.py` and can also be called via the local Python environment. Retry only failed or missing operations after addressing the failure. Do not rerun completed work unless asked to refresh it.

## Verify and report

Read the affected records back through DoorKnock's job detail and recon handlers or the equivalent UI. Check the saved descriptions and source links, one record per listing, and the expected application stage for each record. For completed analysis, confirm stored `analysis_json` and `suitability_score`. For completed Company Recon, confirm both persisted research and `company_recon_status = completed`. Report created and reused counts, any failed or pending operations, and fit scores if generated. Identify material source gaps and describe the provider's team and manager assessments as inference where unverified.
